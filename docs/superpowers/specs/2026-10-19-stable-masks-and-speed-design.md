# 打码观感与速度：固定检测档位、一个目标一个平滑框、固定网格马赛克

日期：2026-10-19。前置：`docs/superpowers/specs/2026-10-18-redaction-proxy-validation-design.md`（`vc_redact` 流水线）、`docs/reports/proxy-validation-2026-10-19-yunet.md`（r3 + YuNet 的现状）。

## 1. 背景与目标

用户看了 64 分钟全片的打码结果后，反馈了四个问题：

1. 希望检测频率可选（5/10/15/30），其余帧靠推算，以提速；
2. 打码区域在很短时间内变化太快，误打面积常常很大，影响观看；
3. 速度慢；
4. 需要新机器部署，含 Linux 和 NVIDIA。

第 4 点另起一份设计。本文只处理 1–3。

### 现状实测（全片 229,606 帧，r3 + YuNet，10 fps）

- **时间：** 主线程忙碌 1491 s，其中检测 1314 s（每个关键帧 34 ms：学生模型约 23 ms + YuNet 约 11 ms，串行）、补框 151 s、打码 25 s。解码和编码与之并行，不是瓶颈。吞吐 152 fps。
- **打码面积：** 每帧平均 4.4%，p95 12%，p99 25%，最大 79%。8.6% 的帧超过 10%。
- **跳变：** 相邻两帧之间，打码区域变化超过画面 1% 的帧对占 20%。
- **每帧打码框数：** 中位数 37，p95 108，最多 241。
- **面积来源：** 按打码框面积算，"扫过区域"（`extended`）占 61%，插值占 32%，关键帧上检测到的框只占 7%。
- **马赛克闪烁：** 分块网格从每个打码框的左上角起算，块大小随框大小变化（长边 / 8，至少 16 px），所以框一动，图案就整片重排。

### 用户已定的取舍

- **观看体验优先：** 接受召回小幅下降，目标人脸 ≥ 95%、车牌 ≥ 98%。
- **检测频率固定：** 运行时选档位，不自动切换。
- **补框改为"一个目标一个平滑框"。**

## 2. 检测频率与速度

- **固定检测频率，档位跟随视频帧率。**
  - **取值范围：** `detect_fps` 可取 5 到 60 之间的数（不超过 60）。推荐档位是 5、10、15、30、60 中不超过视频帧率的那些：60 fps 视频可用 5/10/15/30/60，30 fps 视频可用 5/10/15/30，25 fps 视频可用 5/10/15（另加 25 = 逐帧）。
  - **按帧序号等间隔：** 关键帧每隔 `stride` 帧产生一次，`stride = max(1, ⌊视频帧率 / detect_fps + 0.5⌋)`，整段不变。因此 `detect_fps` 达到视频帧率时就是逐帧检测。实际检测频率 = 视频帧率 / `stride`，写进 `stats.json`（`detect_fps_actual`）和命令行摘要。例如 25 fps 视频选 10，`stride` 为 3，实际 8.3 次/秒。
  - **请求值超过视频帧率时：** 按逐帧检测处理，stderr 打印一行说明。超过 60 或低于 5 视为参数错误（退出码 2）。
  - **视频帧率：** 取视频流的平均帧率（`avg_frame_rate`）；读不到时退回 `r_frame_rate`，再读不到就报错。
  - 去掉"画面运动大就升到 `max_detect_fps`"的逻辑。`RedactConfig` 删除 `max_detect_fps` 和 `motion_threshold` 两个键；配置文件里出现这两个键时报错，并说明它们已删除。
  - `vc_extract` 的抽帧逻辑不变（它仍用 `FrameSampler` 的运动档）。
  - "缓冲满 120 帧强制出一个关键帧"的保护保留，对 5 档以上的任何帧率都不会触发。
- **默认 10。** `configs/redact.json` 里 `detect_fps` 为 10。`scripts/redact.sh` 增加环境变量 `VC_DETECT_FPS`，映射到 `--detect-fps`。`docs/USAGE.md` 列出各档位的实测速度。
- **两个检测器并行。**
  - 每个关键帧上，`MergedDetector` 同时跑学生模型和 YuNet（两个线程），等两者都返回后合并，合并规则不变。
  - 任一检测器抛错，整次运行失败，与现在一致。
  - 两个 onnxruntime 会话互相独立，各自持有输入缓冲。
  - `stats.json` 的 `detect` 计时改为墙钟时间，另记两个检测器各自的忙碌时间（`stages.detect_student`、`stages.detect_face`）。
- **预计吞吐（M5，1080p60）：** 5 档约 250 fps（编码成为上限）、10 档约 210、15 档约 150、30 档约 80、60 档（逐帧）约 40。实现后以实测为准，写进 `docs/USAGE.md`。

## 3. 补框：一个目标一个平滑框

`BoxTimeline` 的输出改为：**每条轨迹每帧至多一个打码框**。匹配规则保留现有的两轮：严格一轮加宽松一轮，同类、尺寸相差 3 倍以内。

### 3.1 位置与大小

- **两端都检出时：** 关键帧 k0、k1 之间的帧 t，原始框 = 两端检测框按 (t − k0)/(k1 − k0) 线性插值（中心和宽高分别插值），再按 `expand_fraction` 外扩、按 `min_box_px` 撑到最小尺寸。
- **`motion_expand_fraction`** 保留：按每个间隔的位移额外外扩，用来吸收非线性运动的插值误差。数值在校准时重新确定。
- **大小迟滞，变大及时、变小慢。** 平滑的是大小，不是各条边。每条轨迹维护平滑后的宽 W 和高 H：
  - 每一帧，原始框（插值、外扩、撑到最小尺寸之后）宽 w、高 h、中心 c：w ≥ W 时 W′ = w，否则 W′ = max(w, W·(1 − `shrink_per_frame`))（默认 0.02）；H′ 同理；
  - 输出框以原始框的中心 c 为中心、大小 W′ × H′，所以始终包含原始框、跟着目标走，不会沿运动方向拉长；
  - 新轨迹从 W = w、H = h 开始；目标丢失、原地保持的帧保留最后的 W、H（不收缩），放在保持的位置上。
- **面积上限：** 输出框面积不超过原始框面积的 `max_mask_area_ratio`（默认 4）倍。超出时，W′ 和 H′ 按同一比例向 w、h 收缩到恰好满足上限（闭式解）。

### 3.2 删除的行为

- 没配上的轨迹沿速度向前和向后扫过的区域（`extended` 打码框不再产生）。
- 宽松配对与首次配对时，在整个区间保留的两端原地框。
- 从幽灵猜测位置出发的插值，以及"从最后一次真实检测插值"的那份补充框。

### 3.3 目标丢失

- **原地保持：** 轨迹在 k1 没有配上时，[k0, k1) 内的框在 k0 的检测框处原地保持。若已知速度，按速度外推，但整个间隔的总位移不超过 0.5 个边长。
- **重新检出：** 轨迹在下一个关键帧 k2 仍可被匹配（幽灵，现有的 `kMaxMissedKeyframes = 1`）。配上了，[k1, k2) 就从保持位置插值到 k2 的检测框；没配上，轨迹在 k1 结束，[k1, k2) 不再打码。
- `masks.jsonl` 里每个框记录 `track`（轨迹编号，整数）和 `origin`。`origin` 取值：`detected`（关键帧）、`interpolated`、`held`（丢失后的保持）。

### 3.4 低分检测的确认

- **确认门槛：** 分数低于本类确认门槛的检测框，只有在相邻两个关键帧都出现（被匹配进同一条轨迹）时才打码。新配置键 `face_confirm_score`（默认 0.5）、`plate_confirm_score`（默认 0.15）。门槛按类别判断，与来源无关（学生或 YuNet）；合并框按合并后的分数（两者较大值）判断。
- **不增加延迟：** 区间 [k0, k1) 的帧本来就要等 k1 的检测结果出来才输出，所以确认在 k1 做出。确认后，这条轨迹从 k0 起打码。
- **没确认的单次低分检测：** 不打码，记入 `detections.jsonl`，并标记 `confirmed: false`。
- **高分检测：** 出现即打码，与现在一致。
- **已确认的轨迹：** 后续的低分检测不需要再确认。

### 3.5 已知代价（接受）

- 只被低分检到一次的真目标会漏，例如快速横穿、只露一次的小脸。
- 在两个关键帧之间掉头的目标，那个间隔内可能盖不全。
- 第一次被检出之前的帧不打码。**这是一处改动，不是现状**：旧代码会把新出现的目标往前一个间隔原地补打（`extended`），本设计把它和其他扫过区一起删掉了。它和"连续漏检两次轨迹就结束"叠加时，检出模式为"检到、漏、漏、检到"的目标会有两整段不打码（旧代码能兜住）。验收时专门统计这类漏遮。

### 3.6 大人脸要更高分（2026-10-20 验收后补充）

- **起因：** 校准后的全片验收，每帧打码面积最大值 40.9%（目标 ≤ 30%）。超过 30% 的 64 帧（12 段，每段 ≤ 0.3 秒）都是 YuNet 把路面、楼群、隧道墙认成大脸：全片 81 个超过画面 5% 的人脸检测框全部来自 YuNet，分数 0.30–0.58（中位数 0.33），其中 51 个过了低分确认；学生模型没有这么大的人脸框。
- **规则：** 类别为 `face`、检测框本身（外扩之前）的面积超过画面面积的 `large_face_area_fraction`（默认 0.05），且分数低于 `large_face_min_score`（默认 0.6）的检测框直接丢弃：不进补框、不打码、不写 `detections.jsonl`。按类别判断，与来源无关；合并框按合并后的框和分数判断。范围：`large_face_area_fraction` 在 (0, 1]，`large_face_min_score` 在 [0, 1]（取 0 即关闭）。
- **记录：** 丢弃的个数写进 `stats.json` 的 `large_faces_dropped` 和运行结束的统计行。
- **代价（接受）：** 离镜头很近、分数又低于 0.6 的真人脸会漏。行车视频里人脸占画面 5% 以上很少见，YuNet 对这么大的真脸给分通常很高。

### 3.7 连续两次漏检的幽灵段（对比实验）

- **起因：** 参照帧每 48 帧一张，10 档每 6 帧一个关键帧，所以参照帧全是关键帧，P1 召回量不到关键帧之间的补框。用逐帧检测作参照的时间覆盖显示，新设计在关键帧之间的覆盖比旧代码低（中分人脸 97% → 90%）；每段两分钟视频约 500 次"检到、漏、漏、检到"的空档，解释了约四分之一的关键帧间漏遮。
- **开关：** `hold_lost_ghosts`（JSON 布尔，默认 `false`）。为 `true` 时，幽灵在下一个关键帧 k2 没配上，[k1, k2) 仍在幽灵的保持位置打码（`origin` 为 `held`，位置不再移动，运动外扩为 0；`held` 帧本来就不缩小，所以大小延续保持段的大小），然后轨迹结束；视频最后一个关键帧之后的尾段里，幽灵同样在保持位置打码。空档从两个间隔缩到一个；代价是消失的目标（包括误检）多留一个间隔的码。
- **默认值：** 在两段校准视频上对比开、关两种情况的时间覆盖（按分数段）、空档次数和观感指标后定。

### 3.8 低分配对只走严格的第一轮（2026-10-20 验收后补充）

- **起因：** 加了 §3.6 后，全片面积最大值仍是 39.2%，超过 30% 的 15 帧都出在第 20862–20874 帧：右上角一条 YuNet 低分人脸轨迹（0.33，占画面 2%）在第 20874 帧被宽松的第二轮配上了左下角远处的另一个低分人脸（0.31），插值框斜穿画面，加上运动外扩，框被撑到画面的 39%。
- **规则：** 配对的任一端低于本类的确认门槛（`face_confirm_score` / `plate_confirm_score`），这一对只能在第一轮（`match_max_distance`）配上，不进第二轮。轨迹一端按它最后一次真实检测（幽灵按丢失前那次检测）的分数算，新框按它自己的分数算；没有确认门槛的类别不受影响。两端都不低于门槛的配对照旧走两轮。
- **代价（接受）：** 在一个间隔里移动超过一个边长、且某一端分数偏低的真目标会断成两条轨迹：旧轨迹按 §3.3 保持、留幽灵；新框若是低分，要按 §3.4 重新确认。

## 4. 马赛克：固定在画面坐标的网格

- **块大小按轨迹固定。**
  - 轨迹开始时，块大小取档位表 {16, 24, 32, 48, 64, 96, 128, 192, 256} 中第一个不小于 `max(mosaic_min_block_px, ⌈长边 / mosaic_blocks_per_long_side⌉)` 的值；
  - 之后只有当这个计算值超过当前块大小的 1.5 倍时才升档，不降档；
  - 块大小随打码框一起记入 `masks.jsonl`（`block` 字段）。
- **网格对齐整幅画面。**
  - 打码区域的四边向外扩到块大小的整数倍坐标：x1 = ⌊x1 / b⌋·b，x2 = ⌈x2 / b⌉·b，再裁到画面内；
  - 每块取块内均值；
  - 色度平面按色度子采样换算块大小与坐标（4:2:0 时为 b/2）。
- **车牌不向外对齐（2026-10-20 补充）：** 车牌的打码区域保持打码框本身，不扩到块的整数倍；仍按同一张画面网格分块，被框边切开的块取框内那部分的均值，色度覆盖框内像素用到的全部色度样本。`masks.jsonl` 每个框记 `snap`（车牌 `false`，其余 `true`），`vc_eval` 的屏上面积按它计算。
  - 起因：车牌检测框与老师标注基本一样大（宽高比中位数 1.01），但三段验收视频里车牌的屏上面积是检测框的 5.4–5.8 倍（中位数约 9–10 倍）：外扩与最小尺寸约 2.3–2.6 倍，向外对齐 16 px 网格再乘约 2.3 倍（车牌高度中位数只有 8–9 px，打码框高约 16 px，对齐后几乎都成 32 px）。
  - 效果（用已有输出估算）：车牌屏上面积降到原来的 42–44%；人脸不变。
- **重叠的打码框：** 按块大小从大到小依次打码。
- **不再有"窄于半块的尾块并入"规则**，因为边界已经对齐网格，画面右、下边缘的不完整块直接取实际像素的均值。

## 5. 评测（`vc_eval`）

- **观感指标，每次运行都算：**
  - 每帧打码面积（各打码框按像素取并集）的均值、p95、p99、最大值；
  - 帧间跳变：相邻帧打码区域异或面积超过画面 1% 的帧对占比；
  - 每帧打码框数的中位数和 p95；
  - 同一帧里同一 `track` 出现不止一个框的帧数，应为 0。
  - 写进 `summary.json`，`summary.md` 里加一节"观感"。
  - 用 1/4 分辨率栅格计算全部帧，不抽样。
- **参照误检排除：**
  - 若 `data/labels/<段>/excluded_refs.csv` 存在（列：`frame,cls,x1,y1,x2,y2,reason`），与其中某一行同帧、同类、IoU ≥ 0.5 的参照框不计入召回；
  - `summary.md` 写明每段排除了多少个、原因分别是什么；
  - 文件由人工核查后填写（本轮把已核查的公交尾灯、警示牌、水马、LED 屏等写进去）。
- **召回目标可配置：** `vc_eval run --recall-target face=0.95,plate=0.98`。默认仍是 0.99（主设计的生产目标）。

## 6. 验收

在留出段 1200s、2400s 上校准（`shrink_per_frame`、两个确认门槛、`expand_fraction`、`motion_expand_fraction`），在从没用过的 60s 段和 64 分钟全片上确认。

| 方面 | 现在 | 目标 |
|---|---|---|
| 人脸召回（排除参照误检后，三段合计） | 48/48 | ≥ 95% |
| 车牌召回（同上） | 766/768 | ≥ 98% |
| 每帧打码面积 p99 | 25% | ≤ 10% |
| 每帧打码面积最大值 | 79% | ≤ 30% |
| 帧间跳变（> 1% 画面的帧对占比） | 20% | ≤ 5% |
| 同一轨迹在同一帧有多个框的帧数 | （现在没有轨迹编号） | 0 |
| 速度（10 档，M5，1080p60） | 152 fps | ≥ 200 fps |
| 输出完整性 | 通过 | 通过 |

另外，在全片上抽几个时间点做打码前后的对比图，交给用户人眼确认（P4）。

## 7. 测试

- **`BoxTimeline`：**
  - 每条轨迹每帧至多一个框；
  - 插值位置；
  - 迟滞（立即变大、每帧收缩不超过上限、输出框始终包含原始框并以它为中心、快速移动的目标不沿运动方向拉长、丢失后保持大小）；
  - 面积上限；
  - 丢失后原地保持与外推上限；
  - 幽灵再匹配；
  - 低分单次检测不打码、两次确认后从首次出现起打码、高分立即打码；
  - 不再产生 `extended`。
- **马赛克：** 网格对齐（同一像素在框平移前后落在同一块里，块值相同）、块大小档位与升档、色度换算、画面边缘的不完整块、重叠顺序。
- **`MergedDetector`：** 两个检测器并行（用带延时的假检测器证明墙钟时间约等于较慢者）、任一抛错整次失败、合并结果与串行一致。
- **检测档位：** `stride` 的计算（60/30/25/23.976 fps 视频，各档位，含请求值等于或超过视频帧率时逐帧）、5 与 60 的边界、超出范围报错、读不到平均帧率时的退回；`stats.json` 的 `detect_fps_actual`。
- **配置：** 删除的键报错、新键的默认值与范围、仓库配置文件等于内置默认值。
- **`vc_eval`：** 观感指标的计算（构造已知面积和跳变的 `masks.jsonl`）、`excluded_refs.csv` 的匹配与报告、`--recall-target`。
- **原有测试：** 依赖旧行为（扫过区、两端保持框、`max_detect_fps`）的测试按新规则改写，并逐一说明。
