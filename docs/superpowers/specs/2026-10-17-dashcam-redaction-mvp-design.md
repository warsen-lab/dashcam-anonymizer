# 行车记录仪视频脱敏（人脸 / 车牌打码）MVP 设计

- 日期：2026-10-17
- 状态：设计已逐节确认，待实施计划
- 范围：MVP，在本机（Apple M5）验证**处理精度**；生产（NVIDIA GPU 服务器）的速度方案只做架构预留和估算

---

## 1. 背景与目标

对行车记录仪拍摄的视频做脱敏：自动定位画面中的**人脸**和**车牌**并打上不可逆的马赛克。

- 输入：4K（3840×2160）60fps，每段 2 分钟。
- 生产速度目标：1 小时视频 ≤ 10 分钟处理完，理想 1–5 分钟。
- 本 MVP 的目标：**先证明精度达标**（见 §8.4 验收条件），同时打通“抽帧 → 标注 → 训练 → ONNX 推理 → 打码输出”全链路，并给出生产速度估算。

## 2. 需求与约束

### 2.1 性能目标折算

| 目标 | 1 小时 4K60 = 216,000 帧，所需端到端吞吐 |
|---|---|
| 10 分钟 | 360 fps |
| 5 分钟 | 720 fps |
| 1 分钟 | 3600 fps |

瓶颈在 4K 的**解码与重新编码**，而不是检测：检测只在关键帧上做（5–30 fps 可配），中间帧由补框得到。1 小时 = 30 段，按段天然可并行。

### 2.2 已确定的约束

| 项 | 决定 |
|---|---|
| 生产硬件 | NVIDIA GPU 服务器（NVDEC/NVENC + onnxruntime CUDA/TensorRT EP） |
| MVP 环境 | 仅本机：Apple M5 / 10 核 / 32GB，ffmpeg 8.1（VideoToolbox），Java 21，CMake，clang++ |
| 数据 | 有原始视频，无标注 |
| 车牌 | 海外车牌。只做定位不做 OCR，跨国家泛化可接受 |
| 精度 | 召回优先：必须遮住目标的逐帧召回 ≥ 99%；误检宽松，只要求无大面积误打 |
| 方案 | 方案 A：老师模型预标注 → 训练 YOLOv8n 双类学生模型；C++ 流水线 |
| 多模态 | **不引入**多模态 / LLM 模型（无本地部署计划，且帧数据含个人信息不外发） |

### 2.3 本机运行约束（来自用户全局规则）

- 本机不跑长时重负载：预标注分批，每批 ≈ 15 分钟以内；每次训练用 `time` 参数封顶 30 分钟；开跑前先告知预计耗时。
- 本机最多同时处理 1–2 段视频；不做全量回灌。
- 计费流量：所有联网步骤（装包、下权重）先列清单与大小，经用户同意再下载；权重缓存放在所有 checkout 共享的 `~/.cache/video-compliance/`，不放进仓库或 worktree。
- 单测/集成测试只跑与改动相关的用例，测试数据由 ffmpeg 本地生成，不联网。

### 2.4 许可证提示

- ultralytics YOLOv8 为 **AGPL-3.0**：闭源商用需购买企业授权，或换 Apache-2.0 检测器（如 YOLOX）。MVP 先用 YOLOv8n；C++ 流水线只依赖 “ONNX + `model.json`” 契约，换模型不改流水线。生产前由用户决定。
- 老师模型只选 MIT / Apache / BSD 许可；InsightFace 系（SCRFD 等，仅限非商业研究）不用。

```

                                    │
                     [Py 老师集成预标注] ─▶ [规则标记疑似漏标] ─▶ [X-AnyLabeling 人工确认 / 金标准]
```

### 3.2 数据契约

**坐标**：所有框一律使用**原始 4K 像素坐标**（x1, y1, x2, y2，左上为原点）。

**`frames.csv`**（vc_extract 输出）

```
video,frame,pts_ms,reason,motion_score
trip01_0003.mp4,1234,20566.7,motion,0.084
```

`reason ∈ {base, motion, clip}`。

**`detections.jsonl`**（每行一个检测；C++ 学生模型与 Python 老师模型共用）

```json
{"video":"trip01_0003.mp4","frame":1234,"pts_ms":20566.7,"cls":"face","x1":812.0,"y1":433.5,"x2":846.2,"y2":475.0,"score":0.87,"src":"student"}
```

`cls ∈ {face, plate}`；`src` 标明来源模型（`student`、`teacher_retinaface`、`teacher_yunet`、`teacher_owlv2` 等）。

**`masks.jsonl`**（vc_redact 输出，每帧最终打码框，评测用）

```json
{"video":"trip01_0003.mp4","frame":1235,"boxes":[{"cls":"face","x1":800,"y1":420,"x2":860,"y2":490,"origin":"interpolated"}]}
```

`origin ∈ {detected, interpolated, extended}`。

**标注**：YOLO txt（每图一个，归一化坐标，类别 0=face、1=plate）。金标准额外有 `gold_meta.csv`：`image,video,frame,scene_tags`（如 `day;city;rain`）。

**`model.json`**（与 `model.onnx` 同目录）

```json
{
  "name": "yolov8n-face-plate-r1",
  "classes": ["face", "plate"],
  "input": {"width": 2560, "height": 1440, "color": "RGB", "scale": 0.00392156862745098},
  "output_format": "yolov8",
  "train_manifest_sha256": "…",
  "metrics": {"val_map50": 0.0}
}
```

C++ 从 `model.json` 读取输入尺寸与类别，不写死；`model.json` 与 ONNX 实际输入形状不一致时拒绝启动。

**配置**：JSON（C++ 用 nlohmann/json 解析，与 `model.json`、jsonl 共用一个库）。

### 3.3 关键接口（C++）

```cpp
struct Box { int cls; float x1, y1, x2, y2, score; };

class Detector {              // 输入整帧，输出 4K 坐标下的框
 public:
  virtual ~Detector() = default;
  virtual std::vector<Box> detect(const Frame& frame) = 0;
};

class FrameSource;            // 解码帧（MVP: CPU NV12；生产: CUDA NV12）
class Masker;                 // 在帧上打码
class FrameSink;              // 编码输出
```

生产 GPU 实现只是为这些接口换实现，流水线编排不变。

## 4. 抽帧模块（C++ `vc_extract`）

**职责**：按策略从视频抽帧，输出训练/标注用图片。抽帧策略 `FrameSampler` 与 `vc_redact` 的关键帧选择共用。

**`FrameSampler` 策略**

1. **基础频率** `--fps`，默认 5，**低于 5 报错**；按 PTS 选帧（兼容可变帧率）。
2. **动态加密**：每个解码帧的亮度平面缩到 160×90，与上一帧求平均绝对差作为运动分；超过阈值时把频率提到 `--max-fps`（默认 15）。
3. **近重复去除**（训练采集时开）：候选帧与上一张保留帧的缩略图差异低于阈值则跳过（如停车等灯）。
4. **片段模式** `--clip 起点,时长 --all-frames`：导出一小段的每一帧，供 §8.2 时间覆盖率评测。

**实现要点**

- FFmpeg libav* 顺序解码（长 GOP 下比反复 seek 快），开启硬件加速。
- 运动分只在缩小的亮度平面上算；只有保留帧才做 4K→BGR 和 JPEG 编码（质量 95，约 2–3MB/张）。
- 输出 `data/frames/<视频名>/<帧号:06d>.jpg` 与 `frames.csv`。

**错误处理**

- 单帧解码失败：记日志、跳过、计数。
- 文件打不开或无视频流：非零退出码 + 明确信息。
- 输出目录已存在：默认拒绝，`--overwrite` 才覆盖。
- 结束打印：解码帧数、保留帧数、各 reason 占比、耗时、fps。

## 5. 标注模块（Python `py/labeling`）

### 5.1 类别定义（另写 `docs/labeling-guide.md`）

- `face`：可见五官区域的人脸（正脸、侧脸、挡风玻璃后的司机、**广告牌上的人脸也标**）。只有后脑勺不标。框从额头到下巴。
- `plate`：车辆号牌，前牌/后牌/摩托车牌；部分遮挡也标；形似车牌的非号牌不标。框贴牌照边框。

### 5.2 老师集成预标注

- **人脸**：RetinaFace-R50（MIT）**直接在 4K 整帧上推理**（全卷积，无接缝）。本机太慢时退回切块，并必须满足 §5.4 的覆盖规则。YuNet（OpenCV zoo，MIT）作为第二意见。
- **车牌**：两级。torchvision COCO 检测器（BSD）先找车辆（car/truck/bus/motorcycle）→ 每辆车裁图 → OWLv2（Apache-2.0，提示 `"license plate"`）在车辆小图内找车牌。
- 置信度阈值偏低（初值 0.3），宁可多框；多来源结果用加权框融合合并。

### 5.3 疑似漏标的规则标记（不使用多模态）

| 规则 | 标记条件 |
|---|---|
| 双模型分歧 | RetinaFace 与 YuNet 只有一方检出的人脸 |
| 该有却没有 | 足够大的行人身上无人脸；足够大的车辆上无车牌（行人背对时会误报，人工排除即可） |
| 前后帧补洞 | 同一目标在 t−1、t+1 帧检出而 t 帧没有 → 自动补框并标记（片段模式 / 密集抽帧处最有效） |
| 低分框 | 0.3–0.5 分的框进入人工确认队列 |

阈值（“足够大”的尺寸等）写在 `configs/labeling.json`。被标记的帧在 X-AnyLabeling（本地桌面工具，读写 YOLO 格式）中人工确认。

### 5.4 切块覆盖规则（仅老师退回切块时适用）

块之间重叠 **O ≥ L + 2m**，其中 L = 小目标最大尺寸（256px），m = 边距（64px）。由此，任何尺寸 ≤ 256px 的目标都完整落在某个块内且距块边 ≥ 64px；更大的目标由“整帧缩到 1/3”的那一遍负责（缩后仍 ≥ 85px）。该性质由单测验证（随机生成目标框，断言存在满足边距的块）。

### 5.5 人工金标准与数据划分

- **按视频划分**训练 / 验证 / 金标准，同一视频的帧不跨集合（相邻帧高度相关，按帧切分会让评测虚高）。
- 金标准来自留出视频，按场景分层抽帧（白天/夜间、城区/高速、雨天、隧道），在 X-AnyLabeling 中逐帧修正。
- **金标准规模按目标数定，不按帧数定**：每类“必须遮住”的目标至少 500 个，初始约 300 帧，不够就继续加帧。报告同时给出召回率的 95% 置信区间。

### 5.6 本机耗时控制

预标注按批跑（每批 ≈ 15 分钟以内），开跑前告知预计耗时。

## 6. 训练模块（Python `py/training`）

- **模型**：YOLOv8n，2 类（face、plate），从 COCO 预训练权重微调。
- **训练时随机裁块、推理时整帧**（解决 4K 小目标问题，同时避免切块推理的接缝盲区）：
  - 训练样本：从 4K 帧**随机位置**裁 1920×1920 区域，缩放 0.67 得到 1280×1280 样本（与推理尺度一致），保证每个标注目标至少完整出现在一个裁块中；裁块内可见面积 < 30% 的框丢弃。另混入一部分整帧缩到 1/3（1280×720）的样本，让模型见过完整大目标。
  - 推理：整帧缩放后一次推理（0.67 → 2560×1440；0.5 → 1920×1088），**无接缝**；计算量与 2×2 切块相当。
  - 小目标召回不足时的备选：YOLOv8n-P2（多一个 stride 4 检测头）。
- **训练设置**：imgsz 1280；增强用 ultralytics 默认（含 mosaic 与尺度增强）；本机 MPS，每次 `time` 封顶 30 分钟；ultralytics mAP 只用于观察趋势，验收以 §8.4 为准。
- **难例回流**（MVP 内最多一轮）：第一轮评测的漏检与疑似漏标帧经人工确认后加入训练集，再训一轮。
- **导出**：ONNX opset 17，静态输入（1×3×1440×2560 或 1×3×1088×1920），图内不含 NMS。导出后对 20 张图比对 PyTorch 与 onnxruntime 输出，框差 < 1px。产物 `data/models/<run>/model.onnx` + `model.json`。

## 7. 脱敏流水线（C++ `vc_redact`）

### 7.1 数据流（单遍解码 + 前瞻缓冲）

```
解码线程 ──▶ [缓冲：两关键帧之间的帧，5fps 时约 12 帧 ≈ 150MB] ──▶ 打码 ──▶ 编码线程
   │                 ▲
   └─ FrameSampler 选关键帧 ─▶ Detector ─▶ BoxTimeline（逐帧打码框）
```

线程之间用有界队列连接。

### 7.2 组件

**VideoReader / VideoWriter**

- FFmpeg libav*；硬件后端可替换：MVP 用 VideoToolbox（`hevc_videotoolbox`），生产用 NVDEC/NVENC，`libx265` 作软件兜底。
- 输出与原片对齐：分辨率、帧率、编码格式、码率；PTS 原样透传保证音画同步；音频流直接拷贝。
- **GPS 等数据流默认丢弃**并在日志中列出；`--keep-streams` 保留。

**OnnxYoloDetector**

- 整帧缩放到 `model.json` 的输入尺寸 → ORT 推理（MVP：CoreML EP；生产：TensorRT/CUDA EP；CPU 兜底）→ 按类别 NMS（IoU 0.5）→ 坐标映射回 4K。
- 置信度阈值初值 0.15，最终按“验证集召回 ≥ 99%”调定。

**BoxTimeline**（召回关键）

1. **跨关键帧关联**：同类框按“中心距离 / 框尺寸”配对，并结合匀速运动预测（高速运动时前后框可能不重叠，不能只靠 IoU）。
2. **配上的**：中间帧线性插值。
3. **没配上的**（出现/消失）：在时间上前后各延长一个关键帧间隔；已有速度估计时沿速度方向外推。
4. **外扩**：比例外扩（初值每边 15%）+ 按关键帧间位移量的附加外扩；过小的框补到最小尺寸。

参数在 `configs/redact.json`，由 §8 实验调定。若插值无法达到 99%，后续再引入逐帧光流跟踪（MVP 不做）。

**Mosaic**

- 直接在 NV12 上像素化：每块 Y、UV 分别取均值，不做整帧 RGB 转换（生产可直接改为 CUDA kernel）。
- 块边长 = max(16px, ⌈框长边 / 8⌉)，即沿长边最多 8 块、每块至少 16px，保证车牌字符不可还原。

### 7.3 错误处理：宁可失败，也不输出没打码的内容

- 先写临时文件，**成功后原子重命名**；失败删除半成品。
- 检测器任何错误（ORT 报错、`model.json` 与 ONNX 不符）→ 整段中止，非零退出码。
- 个别帧解码失败 → 记录计数，统计中报告丢帧数。
- 产出：脱敏视频、`detections.jsonl`、`masks.jsonl`、分阶段耗时（解码 / 检测 / 补框 / 打码 / 编码各自 fps）。

### 7.4 生产预留（MVP 不实现）

NVDEC → CUDA NV12（帧留在显存）→ CUDA 缩放归一化 → ORT IOBinding（GPU 张量）→ CUDA 打码 → NVENC，4K 帧不回内存。`scripts/` 中的批处理按段并发：生产一卡（或一个 NVENC 单元）一段，本机最多 1–2 段。

## 8. 评测与 MVP 验收（Python `py/eval`）

**最终召回率 ≈ 检测器召回 × 时间覆盖率。**

### 8.1 检测器召回（金标准）

- 学生模型在选定推理尺度下检测，框按流水线同样规则外扩。
- 只统计**必须遮住**的目标：人脸高 ≥ 24px、车牌宽 ≥ 48px（4K 像素）。目标框 ≥ 80% 面积被该帧打码框的**并集**覆盖即算遮住。更小的目标单列“尽力遮挡”，不计入考核。
- **误打面积**：该帧打码框并集中，不与任何金标准框（含小目标）相交的部分的面积，用于 A3。
- 维度：类别；尺寸档（24–48 / 48–96 / 96–192 / >192px）；**6×4 空间热力图**；场景标签。
- 学生与老师在同一金标准上并排对比。
- **漏检图集**：本地静态 HTML，逐个列出漏检目标的裁图和原图位置。

### 8.2 时间覆盖率

- 用片段模式挑约 6 段 × 3 秒的**难例片段**（对向高速来车、行人横穿、转弯、路口），估计偏保守。
- 同一学生模型逐帧检测作参照，与“稀疏关键帧检测 + 补框”的打码框对比；只衡量补框和关键帧间隔带来的损失。

### 8.3 参数扫描

检测频率 {5, 10, 15, 30} fps × 推理尺度 {0.5, 0.67} → 表格：最终召回、本机单帧推理耗时、生产推理开销估算。**选满足召回 ≥ 99% 且开销最小的组合**作为生产配置。

### 8.4 验收条件（全部满足才通过）

| # | 条件 |
|---|---|
| A1 | 最终召回（检测器召回 × 时间覆盖率）**人脸、车牌各自 ≥ 99%**（同时报告 95% 置信区间） |
| A2 | 空间热力图中样本量 ≥ 30 的格子，召回均 ≥ 97% |
| A3 | 金标准帧中，没有任何一帧的误打面积超过画面 5% |
| A4 | 输出可正常解码；帧数、时长与原片一致（±1 帧）；音频保留；音画同步 |

**速度只报告、不验收**：给出本机一段 2 分钟视频的各阶段 fps 与占比，按“单段耗时 = 最慢阶段、段间并行”估算生产所需卡数。生产吞吐实测是 MVP 之后的第一项工作。

### 8.5 MVP 数据量

至少 15 段 2 分钟视频，来自不同行程与时段（白天/夜间、城区/高速）：约 12 段用于训练与验证（约 1500 帧），其余作为金标准与难例片段。

## 9. 测试策略

## 12. 风险与应对

| 风险 | 应对 |
|---|---|
| 老师标注质量限制学生上限 | 人工金标准独立评测；规则标记疑似漏标；学生与老师并排对比定位差距 |
| 5fps 关键帧达不到 99% | §8.3 扫描，按数据选频率；生产 GPU 可承担 15–30fps 检测 |
| 0.5 尺度小目标召回不足 | 用 0.67 尺度；仍不足则 YOLOv8n-P2 |
| 某些区域系统性偏弱 | 整帧推理无接缝；A2 空间热力图验收 |
| 夜间、眩光、运动模糊 | 金标准分层覆盖；难例回流一轮 |
| 金标准目标数少导致结论不稳 | 按目标数（每类 ≥ 500）定规模，报告置信区间 |
| 本机算力限制下训练不充分 | MVP 结论偏保守；生产前可在 GPU 服务器上用更多数据重训 |
| YOLOv8 AGPL | 流水线只依赖 ONNX 契约，生产前可换 Apache 模型 |
| 打码被还原 | 大块像素化（长边 ≤ 8 块、每块 ≥ 16px） |

## 13. 不在 MVP 范围

- GPU 零拷贝生产实现、批处理服务 / API
- 车牌 OCR；多模态 / LLM 模型
- 人脸、车牌以外的脱敏类别
- 许可证最终决定
- 生产环境吞吐实测（MVP 后第一项工作）

## 14. 决策记录

| 决策 | 理由 |
|---|---|
| 方案 A（老师→学生）而非直接拼现成模型或自建 CNN | 单模型推理最快、贴合行车记录仪画面；老师/学生对比可定位问题；自建 CNN 达到 99% 召回成本过高 |
| C++ 而非 Java | 生产需 GPU 零拷贝；Java 经 JNI 搬运 4K 帧难以达到 360fps |
| 不用多模态 | 用户无本地 LLM 部署计划；云端 API 外发个人数据且占流量 |
| 训练裁块、推理整帧 | 切块推理有接缝盲区和位置偏差；全卷积网络整帧推理计算量相当且各位置一致 |
| 召回优先、误检宽松 | 漏打即隐私泄露，多打代价小 |
| GPS 等数据流默认丢弃 | 位置信息同属隐私 |
| 宁可失败不输出 | 避免半成品被误当作已脱敏视频 |
